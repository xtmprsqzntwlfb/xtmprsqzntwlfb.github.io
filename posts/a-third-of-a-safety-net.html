A Third of a Safety Net: What My Horizon Plugin Wasn't Checking

September 30, 2026

I have been building a small Horizon plugin called Astrolabe. It does one thing: you click around the admin dashboard as usual, and afterwards it shows you the openstack commands and curl calls that would have done the same work. Middleware watches form submissions on their way through, a panel renders what it saw. No database, no new API.

The interesting part is the rules. Each one is plain Python data describing a Horizon form: which class it is, which fields matter, where they land in a REST body: 

{
    "id": "flavor-create",
    "title": "Create flavor",
    "url": r"/admin/flavors/create/?$",
    "form": "openstack_dashboard.dashboards.admin.flavors.workflows"
            ":CreateFlavorInfoAction",
    "command": ["openstack", "flavor", "create"],
    "fields": [
        opt("vcpus", "--vcpus", cast="int"),
        opt("memory_mb", "--ram", api="ram", cast="int"),
        arg("name"),
    ],
}

Which means Astrolabe is a description of code it does not own, kept in a separate repository on a separate release cadence. Not that the change would escape me — I am Horizon's PTL, so the patch that moves a panel goes past me either way. Seeing that patch and remembering that a plugin in another repository quietly leaned on the old path are two different acts, and only one of them is reliable.

Horizon will move, and I will know about it. Astrolabe needs to know without me.

The self-check I was pleased with

So I wrote one early. rules.validate() imports the Horizon form class each rule names, reads its base_fields and confirms every field the rule mentions still exists. A rename upstream becomes a logged warning instead of a command that loses a flag without saying so.

It runs as the fourth layer of the test suite, the one that needs an actual Horizon checkout on the path, and it reported nothing wrong across all ten rules. I was pleased with it in the specific way you are pleased with a thing you built to catch a problem you have not had yet.

The panel that recorded nothing

The first crack showed up while testing against devstack. I created a role through Identity → Roles, went to the Astrolabe panel and found it empty. Deleted one. Still empty. Every other panel I tried was fine.

The rule was correct. There was no form.

Horizon ships the roles panel as its AngularJS variant by default, through ANGULAR_FEATURES['roles_panel'], and that variant POSTs JSON to the /api/* proxy rather than submitting a Django form. Worse, in that mode the Django create view is not routed at all, so the URL my rule was waiting on did not resolve to anything. Flipping the flag in local_settings.d brought both the panel and the recording back: 

# local_settings.d/_11_toggle_angular_features.py
ANGULAR_FEATURES.update({'roles_panel': False})

Not a bug, a mode — and one that will sort itself out as the Angular panels leave. What stayed with me was the shape of the failure. A rule can be entirely accurate about a form and still never see a single submission, and nothing in my weekly job had an opinion about that.

Three ways a rule rots

Sitting down to enumerate it properly, a rule depends on three separate facts about Horizon, and each can change without the others:

  • the form class and its field names
  • the URL path the rule matches on
  • the table name that delete actions arrive under

validate() was checking the first one.

The second is the dangerous one. If Horizon moves a panel's path, the form class imports cleanly, every field is precisely where the rule says it is, the self-check reports no problems and the rule never matches again. Nothing looks wrong from the inside. The plugin just silently stops recording that panel, and keeps doing so until somebody notices a gap in a log they were not watching closely.

The third is the same failure on the delete side. Horizon encodes table actions as <table>__<action>__<id>, so a renamed table means deletes stop being recognised while the create rule for the same resource carries on working perfectly.

I found that out by writing a comment. Having decided the check deserved to run on its own, I gave it a weekly GitHub Actions job against Horizon master, installed under OpenStack's upper-constraints so a red run would mean my rules had drifted rather than pip having had an interesting morning. Then I sat down to write the header comment describing what the job did not cover, got two lines in and stopped.

Reversing the URL instead of pinning it

The fix was to make a rule say where it lives, not only what it looks at. Each one now carries the Horizon URL names it serves: 

"routes": [
    "horizon:admin:routers:create",
    "horizon:project:routers:create",
],
"url": r"/(admin|project)/routers/create/?$",

validate() calls Django's reverse() on each name and checks the rule's pattern still matches the path that comes back. Reversing rather than hard-coding a path is the entire point: the URL name is Horizon's stable handle and the path is the thing upstream is allowed to change. A TABLES entry names the DataTable class its key came from, and the same pass confirms the class still calls itself that.

The first run taught me something I had been carrying around as folklore. Of the eleven URL names now recorded, four reverse without a trailing slash: 

horizon:admin:volume_types:create_type   /admin/volume_types/create_type
horizon:identity:projects:create         /identity/create
horizon:identity:domains:create          /identity/domains/create
horizon:identity:groups:create           /identity/groups/create

Which is why every pattern ends in /?$, and why project-create matches /identity/create with no panel slug in it at all. That was previously a thing I knew and nothing enforced. Any reasonable tidying pass would have removed it and broken four rules in a way no test could see.

A check that cannot fail is decoration

Adding the checks was the easy half. The half that mattered was proving they bite, because a self-check that has never reported anything is indistinguishable from one that cannot. So each failure mode gets a test that stages it deliberately and asserts it comes back: 

- flavor-create: horizon:admin:flavors:nope no longer reverses;
  the rule cannot fire
- volume-type-create: horizon:admin:volume_types:create_type is now
  /admin/volume_types/create_type, which '/admin/volume_types/moved/?$'
  does not match
- table roles: ...identity.users.tables:UsersTable now calls itself
  'users', so deletes there stop being recorded

The middle one is the test I would keep if I could only keep one. It leaves the form completely untouched and changes nothing but the path, which is exactly the situation the old check looked at and called healthy.

What I took from it

None of this was subtle. I had written a check for the failure I happened to imagine — a renamed field — and then read its green result as a statement about the whole rule. A self-check only covers what you thought of while writing it, and it will go on reporting confidently about everything else.

The useful exercise turned out to be boring and mechanical: list every external fact the thing depends on, then count how many of them the check can actually observe. One out of three, in my case, and I only counted because I had to describe the gap in writing.

The alternative is to carry it in my head: Astrolabe's rules alongside everything else Horizon is doing. That holds until the week it does not, and it makes every upstream change somebody's unpaid chore. A check that runs on its own schedule costs a morning to write and never has a busy week.

Green does not mean correct. It means the things you remembered to look at have not changed.
